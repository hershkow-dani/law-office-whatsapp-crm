# ארכיטקטורה והחלטות טכניות

מסמך זה מרכז את כל הפרטים הטכניים המלאים של המערכת. לסקירה כללית קצרה ולהרצה מהירה — ראו
[README.md](../README.md) בשורש הפרויקט.

**שלב א׳**: תשתית חיבור WhatsApp והגדרות זהות/מדיניות למשרד.
**שלב ב׳**: מנוע שיחה (מדומה, ללא WhatsApp חי), חילוץ שדות מטקסט חופשי, ניהול תיקים ומשימות, ודוחות/ניקוד.
**שלב ג׳**: תבניות מסמכים ויצירת מסמכים ממולאים אוטומטית מנתוני תיק/שיחה.

הלקוח מנהל שיחה טבעית ב-WhatsApp מול המשרד; מאחורי הקלעים המערכת שומרת את הגדרות המשרד, ממירה את השיחה
לשדות וסטטוסים, ומחליטה מתי לענות אוטומטית ומתי להעביר לאדם. **אין עדיין חיבור אמיתי לרשת WhatsApp** —
ראו "מה נדרש לחיבור חי" למטה. שלב ב׳ מדמה הודעות נכנסות/יוצאות דרך אותו מודל נתונים ומנוע החלטה, כך
שהחיבור בעתיד לספק אמיתי הוא רק החלפת שכבת השילוח (`server/src/engine/provider.ts`), לא שינוי לוגיקה.

## מבנה הפרויקט

```
/                 לקוח: React + Vite + TypeScript (הגדרות משרד + שיחות/תיקים/דוחות)
/server           שרת: Node + Express + TypeScript + SQLite (better-sqlite3)
/server/src/engine/decision.ts    שעות פעילות + תנאי העברה לאדם (שלב א׳)
/server/src/engine/provider.ts    הפשטת שליחת WhatsApp — כרגע רק MockWhatsappProvider
/server/src/engine/extraction.ts  חילוץ שדות מבוסס-מילות-מפתח (תחום עיסוק, דחיפות, טלפון)
/server/src/engine/autoReply.ts   בניית תגובה אוטומטית משילוב הגדרות המשרד + מנוע ההחלטה
/server/src/engine/scoring.ts     ניקוד 0-100 לפי זמן תגובה, שלמות שדות, נכונות ההעברה לאדם
/server/src/engine/documentRender.ts   מילוי {{placeholders}} בתבנית מסמך מתוך נתוני משרד/תיק/שיחה
/server/src/engine/inboundPipeline.ts  צנרת "הודעה נכנסת → חילוץ+החלטה+תגובה" משותפת ל-/inbound ולוובהוק
/server/src/engine/webhookSecurity.ts  אימות חתימת X-Hub-Signature-256 של Meta
/server/src/engine/metaWebhookParser.ts   פענוח payload של webhook לרשימת הודעות נכנסות
/server/src/routes/webhooks.ts    נקודת קצה לקליטת webhook (handshake + הודעות נכנסות)
```

### למה הבחירות האלה

- **אין ספק WhatsApp קיים בפרויקט** — לכן שלב א׳ בונה רק את התשתית (הגדרות + מודל נתונים + מנוע החלטה),
  ומתעד בדיוק מה חסר לחיבור חי, כפי שנדרש.
- **SQLite (better-sqlite3)** — מסד נתונים מקומי, ללא תלות בשירות חיצוני, מתאים לשלב תשתית/הגדרות ולריצה
  מקומית על מחשב המשרד. מעבר למסד נתונים אחר (Postgres וכו') אפשרי בעתיד ללא שינוי בממשק ה-API.
  קובץ הנתונים: `server/data/crm.db` (נוצר אוטומטית, לא נכלל ב-git).
- **מודל נתונים מרובה-משרדים (multi-tenant)**: כל טבלה מקושרת ל-`office_id`, כך שאפשר לנהל כמה משרדים
  באותה מערכת בלי תלות זה בזה.
- **מספר WhatsApp לכל משרד**: הטבלה `whatsapp_connections` שומרת מספר+סוג (`existing`/`dedicated`) לכל
  משרד בנפרד. אין שום "מספר מרכזי" של ספק המערכת בקוד.

### הערה סביבתית: `npm run dev` מול `npm run build && npm start`

בסביבת הפיתוח הזו נצפתה קריסה אקראית של `tsx` (ה-loader ש-`npm run dev` משתמש בו) בזמן כיבוי התהליך,
עקב אינטראקציה בין תוסף ה-native של `better-sqlite3` לבין hook הניקוי של Node — לא קשור ללוגיקת האפליקציה
(הבדיקות ו-`node dist/index.js` המבונה רצים בלי בעיה). אם `npm run dev` בתיקיית `server` מתנהג באופן דומה
אצלכם, עדיפה הרצה דרך הקוד המבונה:

```bash
cd server
npm run build
npm start
```

## מה נדרש לחיבור WhatsApp חי (עדיין חסר)

שלב א׳ מכין את השדות והמודל, אך לא מבצע שיחת API אמיתית מול WhatsApp. כדי להפעיל חיבור חי צריך להחליט
ולספק:

1. **בחירת ספק/API**: WhatsApp Cloud API של Meta (ישיר), או ספק BSP כמו Twilio / 360dialog / Gupshup.
   כל אחד דורש הרשמה נפרדת ותהליך אימות משלו.
2. **Business Manager מאומת** מול Meta (או חשבון אצל ה-BSP שנבחר).
3. **אימות מספר הטלפון** שנבחר בהגדרות (`whatsapp_connections.phone_number`) מול הספק — כולל קוד אימות
   SMS/שיחה, ורישום שם תצוגה עסקי.
4. **Access Token / API Key** קבוע לשליחת הודעות, ו-Webhook URL ציבורי (HTTPS) + Verify Token לקבלת
   הודעות נכנסות.
5. **תבניות הודעה מאושרות (message templates)** אם רוצים לפתוח שיחה יזומה (לא בתגובה להודעת לקוח) —
   נדרש אישור Meta מראש לכל תבנית.
6. **מדיניות פרטיות/שימוש** גלויה ללקוח, בהתאם לדרישות הדין ולתנאי Meta.

**עדכון**: שכבת הקליטה (webhook) ומימוש השליחה מול Meta כבר בנויים ומכוסים בבדיקות — ראו "שכבת ה-Webhook"
למטה. מה שנשאר הוא אך ורק הזנת הטוקנים/הסודות עצמם דרך משתני סביבה, ללא כל שינוי קוד.

## מנוע ההחלטה (שלב א׳)

`POST /api/offices/:officeId/decision-preview` מדגים כיצד ההגדרות משפיעות על ההתנהגות המתוכננת: מקבל זמן
(`at`) והודעה לדוגמה, ומחזיר האם השעה בתוך/מחוץ לשעות הפעילות (או חג) והאם ההודעה הייתה גורמת להעברה
לאדם. גם ממשק המשתמש (סעיפים 8 ו-10 בטאב "הגדרות משרד") כולל כפתורי "בדוק" שמריצים תצוגה זו בזמן אמת.

## שלב ב׳: שיחות, תיקים ודוחות

הטאב "שיחות, תיקים ודוחות" בממשק מדמה מה שיקרה כשיהיה חיבור WhatsApp חי:

- **`POST /api/offices/:officeId/conversations`** — פתיחת שיחה מול לקוח (טלפון + שם).
- **`POST .../conversations/:id/inbound`** — מדמה הודעה נכנסת מהלקוח. המערכת: (1) מריצה חילוץ שדות
  (`extraction.ts` — תחום עיסוק מתוך תחומי העיסוק שהוגדרו, רמת דחיפות ממילות מפתח, מספרי טלפון בטקסט),
  (2) מריצה את מנוע ההחלטה של שלב א׳ (שעות פעילות + תנאי העברה), (3) בונה תגובה אוטומטית
  (`autoReply.ts`) המשלבת את הגילוי/נציגה/סגנון/מדיניות שעות של המשרד, (4) שולחת אותה דרך
  `provider.ts` (כרגע מוק), ו-(5) מעדכנת את סטטוס השיחה — `pending_human` אם הופעל כלל העברה, אחרת
  ממשיכה במענה האוטומטי. שיחה שכבר `pending_human` לא מקבלת מענה אוטומטי נוסף (ממתינה לאדם), ורצף
  ההודעות וההקשר שנאסף נשמרים במלואם.
- **`POST .../conversations/:id/outbound`** — תגובה ידנית מאיש/אשת צוות.
- **`POST .../conversations/:id/close` / `/resume-auto`** — סגירת שיחה / החזרתה למענה אוטומטי.
- **`POST /api/offices/:officeId/cases`** — פתיחת תיק, עם או בלי קישור לשיחה קיימת; **`.../cases/:id/tasks`**
  — משימות תחת תיק.
- **`POST .../cases/:id/score`** — מחשב ושומר ניקוד 0-100 (`scoring.ts`): 40% מהירות תגובה ראשונה, 40%
  שלמות השדות שנאספו, 20% האם ההעברה לאדם בוצעה בדיוק כשצריך. זהו קירוב פשוט לשלב ב׳ — ראו "מגבלות" למטה.
- **`GET /api/offices/:officeId/reports/summary`** — סיכום מצטבר: שיחות/תיקים לפי סטטוס, שיעור העברה
  לאדם, ניקוד ממוצע, זמן תגובה ראשונה ממוצע.

### מגבלות ידועות בשלב ב׳

- **חילוץ השדות מבוסס מילות מפתח בלבד** (regex + התאמת שם מדויק לתחומי עיסוק), לא בינת מלאכותית. חילוץ
  מבוסס-NLP/LLM אמיתי ידרוש מפתח API לספק AI (OpenAI/Anthropic וכו׳) — ניתן להחליף את `extraction.ts`
  בלי לשנות את שאר הצנרת, כפי שהוא בנוי כרגע כפונקציה טהורה עם קלט/פלט מוגדר.
- **הניקוד הוא קירוב**: "האם ההעברה נדרשה" מבוסס כרגע על אותו דגל `ever_handoff` כמו "האם ההעברה בוצעה"
  (אין עדיין מקור אמת נפרד ל"מה שהיה צריך לקרות" מול "מה שקרה בפועל").

## שלב ג׳: מסמכים

בטאב "הגדרות משרד" (סעיף 11) כל משרד מגדיר תבניות מסמך משלו — טקסט חופשי עם placeholders בסגנון
`{{clientName}}`. בטאב "שיחות, תיקים ודוחות", בתוך תיק נבחר, אפשר לבחור תבנית וללחוץ "צור מסמך":

- **`POST /api/offices/:officeId/document-templates`** — יצירת תבנית (`GET`/`PATCH`/`DELETE` תואמים).
- **`POST /api/offices/:officeId/cases/:caseId/documents`** — ממלא את התבנית מתוך `documentRender.ts`
  (`buildDocumentContext` + `renderTemplate`): שדות המשרד (שם, כתובת, שם הנציגה) בשילוב שדות התיק/השיחה
  המקושרת (שם לקוח, טלפון, תחום עיסוק, כותרת תיק, תאריך). placeholder שאין לו ערך זמין **נשאר בטקסט
  כפי שהוא** ומדווח ברשימת `missingFields` — כך שמסמך שנוצר לעולם לא "מאבד" בשקט מידע שהמשרד צריך להשלים
  ידנית. הממשק מציג את רשימת השדות החסרים ליד כל מסמך.
- **`GET /api/offices/:officeId/cases/:caseId/documents`** / **`GET /api/offices/:officeId/documents/:id`**
  — שליפת מסמכים שנוצרו.

### מגבלות ידועות בשלב ג׳

- **אין עדיין ייצוא ל-PDF/DOCX** — המסמך נשמר ומוצג כטקסט (RTL) בממשק בלבד. הוספת ייצוא לקובץ אמיתי
  (למשל עם ספריית DOCX בצד השרת) היא הרחבה עתידית שלא דורשת שינוי במנוע המילוי עצמו.
- **אין ניהול גרסאות/עריכה למסמך שנוצר** — כל הפעלת "צור מסמך" יוצרת רשומה חדשה; אין כרגע עריכה של מסמך
  קיים אחרי יצירתו.

## שכבת ה-Webhook (מוכנה, ממתינה לטוקנים)

התשתית לקליטת הודעות WhatsApp אמיתיות בנויה ובדוקה (27 בדיקות ייעודיות), אך **לא מחוברת בפועל** — חסרים
רק הטוקנים/הסודות שרק אתם יכולים לספק, כפי שפורט למעלה. שום שינוי קוד לא נדרש כדי להפעיל אותה, רק הזנת
משתני סביבה.

### מה בנוי

- **`GET /api/webhooks/whatsapp/:officeId`** — ה-handshake החד-פעמי שMeta מבצע בעת רישום כתובת ה-webhook:
  משווה את `hub.verify_token` שהתקבל מול הטוקן שנוצר אוטומטית לכל משרד עם חיבור WhatsApp (מוצג בממשק,
  בתחתית סעיף 1 "חיבור מספר WhatsApp", עם כפתור "ייצור טוקן חדש").
- **`POST /api/webhooks/whatsapp/:officeId`** — נקודת הקצה שMeta תשלח אליה כל הודעה נכנסת. מוודאת את
  חתימת הבקשה (`X-Hub-Signature-256`, מחושבת מול `WHATSAPP_APP_SECRET`) לפני שהיא נוגעת בנתונים — בלי
  `WHATSAPP_APP_SECRET` מוגדר, הנתיב מחזיר 501 ומסרב לעבד כלום (כדי שאי אפשר יהיה "לזייף" הודעות נכנסות
  לפני שהאבטחה מוכנה). לאחר אימות, `metaWebhookParser.ts` הופך את ה-payload של Meta להודעות טקסט, ולכל
  הודעה מאתר/פותח שיחה לפי מספר השולח ומריץ אותה דרך אותה `processInboundMessage` שמפעיל גם הנתיב הידני
  `/conversations/:id/inbound` — כך ששני הנתיבים (בדיקה ידנית מול webhook אמיתי) אף פעם לא יכולים לסטות
  זה מזה.
- **`MetaCloudApiProvider`** ב-`provider.ts` — מימוש אמיתי מול ה-Graph API של Meta (`fetch` ל-
  `graph.facebook.com/.../messages`), שנבחר עם `WHATSAPP_PROVIDER=meta_cloud_api`. זורק שגיאה ברורה
  ומיידית אם `WHATSAPP_ACCESS_TOKEN` או ה-`phone_number_id` (מוגדר לכל משרד בסעיף 1, עם fallback גלובלי
  ל-`WHATSAPP_PHONE_NUMBER_ID`) חסרים — לא נכשל בשקט.

### מה עדיין נדרש כדי להפעיל בפועל

1. `WHATSAPP_PROVIDER=meta_cloud_api` (במקום ברירת המחדל `mock`).
2. `WHATSAPP_APP_SECRET` — מ-Meta App Dashboard, לאימות חתימת ה-webhook.
3. `WHATSAPP_ACCESS_TOKEN` — טוקן קבוע לשליחת הודעות.
4. מילוי `phone_number_id` בהגדרות ה-WhatsApp של כל משרד (או `WHATSAPP_PHONE_NUMBER_ID` גלובלי לבדיקה).
5. הדבקת "נתיב ה-Webhook" ו-"Verify Token" (מוצגים בממשק) בטופס ה-Webhook של Meta, **על גבי דומיין ציבורי
   אמיתי** — לא `localhost`. עד שהשרת רץ בפועל מאחורי כתובת HTTPS ציבורית (למשל דרך פריסה בענן, או מנהרה
   זמנית כמו ngrok לבדיקות), אי אפשר לרשום את ה-webhook אצל Meta.

עד אז, כל הבדיקה נעשית דרך `POST /conversations/:id/inbound` (הכפתורים "שלח" בטאב "שיחות, תיקים ודוחות")
או ע"י הדמיית קריאת webhook חתומה — ראו `server/test/webhooks.test.ts` לדוגמה מלאה כולל חישוב החתימה.
